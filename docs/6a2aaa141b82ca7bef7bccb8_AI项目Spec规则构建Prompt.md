# AI 项目规则规范架构构建指令

> 用途：让具备本地仓库读写能力的 AI Coding Agent 审计现有项目，并建立可维护的规则规范架构。
> 适用环境：Codex、Claude Code、Cursor、Trae、GitHub Copilot Agent，以及其他支持终端和文件操作的编码 Agent。
> 核心原则：先审计、后设计、再迁移；尊重现有规则；单一权威源；按需加载；非破坏写入；自动防漂移。

## 一、适用性评估

### 适用项目

- 单体应用、前后端分离项目、CLI、库、移动端、数据项目和多包工作区。
- Windows + PowerShell、macOS/Linux + POSIX Shell、WSL 或容器环境。
- 已有规则文件的成熟项目，或尚未建立 Agent 规则的新项目。

### 不应直接套用的情形

- 仓库只是生成产物、镜像或只读依赖，规则应维护在上游源仓库。
- 项目已有组织级规则平台且禁止仓库内新增规则文件。
- 当前 Agent 没有文件写权限；此时只输出审计报告和建议补丁，不宣称已实施。

### 与固定模板式指令的差异

本指令不预设项目只有一个 `src/`，不固定创建 `project_spec/`，不默认覆盖 `AGENTS.md` / `CLAUDE.md`，不逐文件维护 SHA Wiki，也不要求生成所有 Agent 工具的重复规则。最终结构必须由项目规模、现有约定和实际使用的工具共同决定。

## 二、可直接复制给 AI Agent 的指令

```text
你是一名工程效能与 AI 规则架构专家。请分析当前仓库，建立或优化一套“短入口、分层规则、单一权威源、自动防漂移”的规则规范架构。

你的目标不是生成尽可能多的文档，而是让后续 AI 和开发者能以最少上下文获得准确约束，并且规则能随项目长期维护。

## 0. 全程约束

1. 先读取当前目录及父级适用的 Agent 指令文件，再执行任何写操作。
2. 把当前工作树和代码视为事实来源；文档与代码冲突时，先验证，不凭经验裁决。
3. 不静默覆盖、删除或缩减已有规则。先审计有效内容和迁移去向，再实施。
4. 保留项目特有业务不变式，不用通用最佳实践替换真实业务规则。
5. 不编造模块、命令、端点、表、组件、测试或流程。无法证实的内容标为“未确认”，不要写成强制规则。
6. 只修改规则、规则文档和经批准的规则检查工具；不要顺便修改业务代码。
7. 未经用户明确授权，不提交、不推送、不建分支、不打标签、不发布，也不修改本地 Git Hook。
8. 发现工作区已有改动时，记录基线并避开无关文件；不要擅自清理或回滚。
9. 所有生成动作必须可重复执行：第二次执行不应复制章节、重建无变化文件或扩大差异。
10. 先运行最小、只读检查；对耗时构建、网络操作和有副作用命令遵守当前 Agent 的审批策略。

## 1. 环境与仓库探测

先识别以下事实：

- 操作系统、Shell、仓库根目录、当前工作目录和 Git 分支/状态。
- 是否为单仓库、monorepo、多工作区或嵌套仓库。
- 根目录到目标文件之间所有适用的 `AGENTS.md`、`CLAUDE.md`、Cursor/Trae/Copilot 规则及组织约束。
- 构建清单和依赖入口，例如 `package.json`、workspace 配置、`pyproject.toml`、`requirements.txt`、`go.mod`、`Cargo.toml`、`pom.xml`、`build.gradle`、`CMakeLists.txt`。
- README、贡献指南、CI、测试配置、发布配置和脚本入口。

跨平台要求：

- Windows/PowerShell 优先使用 `Get-ChildItem`、`Get-Content`、`Select-String`；若已安装 `rg`，搜索优先使用 `rg`。
- macOS/Linux/WSL 可使用 `find`、`sed`、`rg`；不要假设 GNU 专属参数一定存在。
- 需要生成维护工具时，优先选择仓库已有运行时；若没有明显偏好，使用 Python 标准库实现跨平台检查。
- 不为满足模板而额外引入依赖。

输出一份简短的“探测基线”，至少包含项目类型、技术栈、应用/包边界、主要模块、构建测试入口、现有规则入口和未提交文件。

## 2. 项目事实审计

读取足以证实当前架构的文件，不做全仓库无差别灌入。至少确认：

1. 产品或库的职责边界，以及明确不做的事情。
2. 运行时、框架、数据存储、外部集成和部署方式。
3. 后端、前端、测试、脚本、配置、文档等稳定模块边界。
4. 公共组件、公共服务、生成文件和配置权威源。
5. 与正确性直接相关的业务不变式、数据口径和安全约束。
6. 修改不同区域时对应的最小验证命令。
7. 可从配置自动读取的动态信息，如版本号；这类信息不应复制到常驻规则。

对每项信息标注证据类型：

- `已证实`：由代码、配置、测试或当前运行结果直接证明。
- `文档声明`：只在文档中出现，尚未由实现交叉验证。
- `推断`：根据结构合理推断，但没有足够证据。
- `冲突`：两个来源说法不一致，需要确定权威源或修正文档。

规则文件只能把“已证实”或经交叉验证的“文档声明”写成强制项。

## 3. 现有规则审计

扫描当前已有的规则、设计和流程文档，建立以下清单：

| 内容类型 | 当前所在文件 | 是否重复 | 是否过期 | 建议权威源 | 迁移方式 |
| --- | --- | --- | --- | --- | --- |

重点查找：

- 同一内容在 README、Agent 入口、设计文档和 changelog 中重复。
- 规则文件中硬编码当前版本、日期、文件数量、测试数量等易变事实。
- 当前规则与代码、CI 或版本文件冲突。
- 已完成版本流水账混入常驻规则。
- 工具专属格式被误当成所有 Agent 的通用格式。
- 根规则过长，导致每次会话加载大量低频信息。
- 已归档文档仍被描述为当前权威源。

在实施前给出迁移设计，明确每类有效内容的新位置。没有迁移去向的有效规则不得删除。

## 4. 选择规则架构

根据审计结果选择最小充分架构，不机械套模板。

### A. 小型单体项目

适用条件：模块少、业务不变式少、根规则可稳定控制在约 200 行内。

建议：

- 一个当前 Agent 的主入口。
- README 或贡献指南承担通用开发说明。
- 不额外创建模块 Wiki。

### B. 中型或前后端复合项目

适用条件：存在多个技术域、业务口径或任务类型，全部塞进根规则会膨胀。

建议：

- 根入口：只放项目边界、最高频红线、权威源和按需阅读索引。
- 分层规则目录：放业务不变式、后端、前端、测试交付、工作流和模板。
- 自动检查：验证入口同步、必需文件、链接和易漂移内容。

可参考但不强制使用：

rules/
├── README.md
├── overview.md
├── business-invariants.md
├── backend.md
├── frontend.md
├── testing-and-delivery.md
├── workflows/
│   ├── feature.md
│   └── bugfix.md
└── templates/
    └── tech-spec.md

### C. Monorepo 或多产品仓库

适用条件：多个可独立构建、发布或拥有不同规则的工作区。

建议：

- 根入口只定义全仓库规则和工作区地图。
- 在各工作区放置该 Agent 支持的作用域规则；例如 Codex 可使用更深层 `AGENTS.md`。
- 共享规则只写一次，工作区规则只描述差异，不复制根规则。
- 对不支持层级作用域的工具，生成薄入口并链接到共享规则，而不是复制全文。

## 5. Agent 入口策略

先识别仓库实际使用的工具，再决定入口：

| 工具 | 常见入口 | 处理原则 |
| --- | --- | --- |
| Codex | `AGENTS.md` | 支持目录作用域；优先使用现有层级结构 |
| Claude Code | `CLAUDE.md` | 若需与公共入口一致，可做字节一致镜像或短链接式入口 |
| Cursor | `.cursor/rules/` 下规则文件 | 只在仓库已使用或用户明确要求时生成，并遵守当前格式 |
| Trae | 仓库现有 `.trae/` 规则约定 | 先读取现有结构，不假设固定文件名 |
| GitHub Copilot | `.github/copilot-instructions.md` | 只在团队实际使用时生成 |

禁止因为“无法判断当前 Agent”就默认生成所有入口。无法确认时，保留已有入口，并在总结中列出可选兼容层。

若两个入口被项目要求完全一致：

- 明确一个维护动作，例如修改主入口后复制到兼容入口。
- 增加 SHA256 或内容一致性检查。
- 不在两份文件中分别人工维护相同内容。

## 6. 建立单一权威源

为以下信息建立矩阵，每种信息只指定一个权威源：

- 当前版本与 changelog。
- 产品说明与安装使用方式。
- AI 会话最高频规则。
- 当前业务不变式和工程规范。
- 已批准功能设计。
- API 或 Schema 契约。
- 历史设计与过期文档。

其他文档只能摘要并链接，不复制整段动态事实。尤其不要在根规则中维护版本流水账。

## 7. 分层规则内容要求

### 根入口必须包含

- 项目定位和明确边界。
- 首次进入仓库需要执行的准备动作。
- 指令优先级和权威源。
- 最高风险业务/工程红线摘要。
- 稳定目录地图。
- 按任务阅读的规则索引。
- 修改、验证、Git 和安全底线。

### 根入口不应包含

- 历次版本“已落地”记录。
- 可从版本文件读取的当前版本号。
- 每个 API 字段或每个源文件的登记表。
- 已归档设计全文。
- 只对极少数任务有用的长篇排障记录。

### 模块规则应回答

1. 这个模块负责什么，不负责什么？
2. 修改前必须读取哪些入口和契约？
3. 哪些不变式不能破坏？
4. 哪些文件是生成文件或外部权威源，不能手改？
5. 修改后运行什么最小验证？

不要逐文件写百科。只有公共入口、边界、生成物和高风险文件需要显式登记。

## 8. 工作流与 TECH_SPEC

为项目实际需要的任务类型建立简洁工作流。至少考虑新需求和 Bug 修复：

### 新需求工作流

1. 将需求拆成可验收项，标注涉及模块、数据来源和非目标。
2. 定位现有同类实现和调用链，确认权威源。
3. 对行为变化先形成设计或 TECH_SPEC，并获得必要确认。
4. 做最小、聚焦实现，不夹带无关重构。
5. 从最相关验证开始，再按风险扩大范围。
6. 仅在架构、规则或公共契约变化时更新长期规则；不要把每次功能 changelog 写入根规则。

### Bug 修复工作流

1. 用日志、请求、测试或 UI 操作复现，记录期望与实际行为。
2. 从失败点追到根因，不用展示层补丁掩盖数据或契约错误。
3. 搜索相同模式的其他调用点，但只修复已证实的同类问题。
4. 在项目已有测试体系中增加最小回归用例。
5. 运行回归测试、受影响模块验证和必要的更广验证。
6. 只有可复用且高风险的新经验才沉淀为长期规则。

### TECH_SPEC 模板至少包含

- 背景与目标。
- 要做 / 不做。
- 当前事实与证据。
- 方案对比与选择理由。
- 受影响模块、数据流和接口。
- 不变式、风险与回滚方式。
- 验收标准和验证命令。
- 文档与规则更新范围。

不要在每份 TECH_SPEC 中维护独立版本号或永久 commit 流水账；版本历史由仓库既有权威源承担。

## 9. 非破坏迁移

按以下顺序实施：

1. 记录实施前 Git 状态和规则文件哈希。
2. 建立目标目录和导航文件。
3. 将现有有效规则按主题迁移，保留原语义和项目术语。
4. 建立从旧章节到新位置的核对表，确认无有效规则丢失。
5. 最后精简根入口，并生成必要的兼容入口。
6. 更新 README、贡献指南、PR 模板或 CI 中已经失效的规则链接。
7. 新增只读检查工具；除非用户明确要求，不安装 Git Hook。
8. 检查 Git diff，确认没有碰触用户原有改动或业务文件。

若现有规则包含互相冲突的说法：

- 先以代码、配置、测试和运行结果交叉验证。
- 能确定时修正规则并在总结中说明。
- 无法确定时保留为“待确认”，不要选择一个看似合理的版本强行落地。

## 10. 自动防漂移检查

检查工具应只读、快速、无网络、无第三方依赖，并根据项目实际架构选择以下检查：

- 必需规则文件存在。
- 要求镜像的 Agent 入口内容或 SHA256 一致。
- 根入口未超过项目设定的行数/字节阈值。
- 根入口没有硬编码版本文件中的当前版本号。
- 根入口没有重新出现版本流水账标题。
- 规则导航引用的仓库相对路径存在。
- 当前权威源矩阵完整且无重复权威源。
- 规则文件没有占位符、明显死链接或已归档路径被声明为当前依据。

优先把检查接入仓库已有 CI 或提交前检查脚本。接入前确认耗时和权限，不重复运行昂贵构建。

## 11. 验证

实施后至少执行：

1. 规则检查工具自身的语法检查。
2. 规则架构检查，退出码 0 才算通过。
3. Agent 入口一致性检查（如适用）。
4. Markdown 结构、必需链接和占位符检查。
5. 关键词迁移审计：关键业务术语、禁止项、生成文件和验证命令均能在新架构中定位。
6. `git diff --check` 和最终 Git 状态审计。

只修改文档和只读检查脚本时，不要为了形式运行与变更无关的全量业务测试；若改动了 CI/提交前流程，至少验证新增命令能独立成功执行。

## 12. 最终输出

输出一份可核查的总结：

- 适配结论：原架构的可复用点与问题。
- 权威源矩阵。
- 新增、修改、迁移和保留的文件。
- 根入口缩减前后的行数/字节数。
- 自动检查覆盖项和执行结果。
- 发现但未处理的冲突或用户原有改动。
- 明确说明是否提交；未经授权应写“未提交”。

完成判据不是“文件已生成”，而是：有效规则无丢失、入口足够短、细节可按需查到、权威源清晰、检查自动通过、最终差异可解释。
```

## 四、质量检查清单

- [ ] 先读取了仓库级和目录级 Agent 指令。
- [ ] 识别了 OS、Shell、工作区、构建和测试入口。
- [ ] 没有假设项目只有一个 `src/`。
- [ ] 没有默认生成所有 Agent 工具的重复入口。
- [ ] 没有静默覆盖或丢失已有项目规则。
- [ ] 动态版本信息只有一个权威源。
- [ ] 根入口只保留会话必读内容。
- [ ] 分层规则按任务可发现，不是逐文件百科。
- [ ] 检查工具跨平台、只读、快速且无额外依赖。
- [ ] 未经授权没有提交、推送、建分支或修改 Git Hook。
- [ ] 最终 Git diff 中没有用户原有改动或无关业务文件。
