# Bug 修复工作流

## 目标

从可复现证据追到根因，做最小、完整修复，并留下能阻止复发的回归证据。不要用展示层补丁掩盖数据、契约或口径错误。

## 1. 建立基线

1. 读取根规则和涉及模块规则。
2. 记录 Git 状态、当前分支、运行方式和相关版本信息。
3. 区分用户原有未提交改动与 Bug 现场，不清理工作区。
4. 收集错误消息、请求/响应、日志、页面路径、筛选条件和最小样例。

## 2. 明确定义

写下：

- **期望行为**：以业务规则、接口契约或可验证用户需求为依据。
- **实际行为**：包含具体值、状态码、堆栈或截图。
- **复现步骤**：最少输入与操作。
- **影响范围**：哪些端点、页面、数据批次或用户受影响。
- **非目标**：本次不处理的相邻问题。

若无法稳定复现，先增加只读日志或定向探针，不直接猜修复。

## 3. 根因定位

沿真实数据流逐层检查：

```text
用户输入/筛选
-> React state / filter adapter
-> service / HTTP payload
-> Flask 参数解析
-> SQL 过滤与聚合
-> ORM / SQLite 数据
-> 响应适配
-> UI 展示
```

常见检查：

- 前端 import、回调作用域、TDZ、`dataIndex`、日期时区和脏文本。
- 双层 API 包装、可选字段、空数组和 `None`。
- 源表/列名、行粒度、分母为 0、重复聚合和错误过滤器。
- 新开户/存量、互联网引流和主播 token 口径。
- Flask 子线程 context、SQLite 路径和 replace/append 语义。
- SPA 兜底把错误资源返回成 `index.html`。

根因结论必须能解释全部已观察现象，而不只是让一个页面暂时恢复。

## 4. 选择修复层

- 数据源错误：优先修上游 ETL；本项目不新增业务清洗补丁。
- 查询口径错误：修后端过滤/聚合，并验证所有共享调用方。
- API 契约错误：在生产者或集中适配层修复，不在每个页面分别兜底。
- 展示错误：在共享组件/工具或目标页面修复，保持后端语义不变。
- 配置权威源错误：修改权威配置，再验证同步缓存。

搜索相同模式的调用点；只扩展到已证实的同类问题，不做全仓库顺手清理。

## 5. 回归测试

1. 先写或确定能在修复前失败的最小回归场景。
2. 后端核心接口在 `tests/api/` 增加快速用例；页面 Bug 在 `frontend-react/tests/regression/` 增加 Playwright 用例。
3. 测试应断言 Bug 的业务结果，而不只断言页面能打开。
4. 使用隔离数据和确定性日期；不依赖真实外网或用户数据库。
5. 修复后运行回归用例及受影响模块的最小验证。

## 6. 实现与验证

- 只改根因所需文件，保持现有风格和公共边界。
- 不删除兼容逻辑，除非已有证据证明可安全退役。
- 依次运行回归测试、类型/语法、smoke、构建和必要的更广测试。
- 检查错误路径、空数据、边界日期、分母为 0 和重复点击/请求。
- 最后运行 `git diff --check` 并审计工作区。

## 7. 规则沉淀

仅当经验同时满足以下条件才写入长期规则：

- 不是单次拼写或偶发数据。
- 未来开发者难以从代码直接看出。
- 一旦违反会造成高风险业务或运行错误。
- 可以写成明确、可执行、可验证的约束。

否则只保留回归测试、代码修复和交付说明，不把 Bug 时间线塞进 `AGENTS.md`。

## 完成检查

- [ ] 修复前问题可复现，修复后同一路径通过。
- [ ] 根因解释与修复层一致。
- [ ] 回归测试覆盖原始失败条件。
- [ ] 相同共享调用点已审计。
- [ ] 未引入下游口径补丁或无关重构。
- [ ] 验证结果和未运行项已明确说明。
