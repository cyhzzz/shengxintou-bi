# 省心投 BI 库表重构设计（v2）

> 设计时间：2026-07-07
> 背景：业务半年演进——新增「应用市场」大类渠道（小米/华为/OPPO/VIVO/荣耀/苹果，鸿蒙/iOS 待上线）；内容平台新增「快手」渠道（抖音/腾讯/小红书/快手）；技术团队已产出底层→聚合层的中间数据，聚合层与维度层可直接导入，无需自建。
> 设计原则：**DIM/DWD/DWS 三层；所有源文件 1:1 落表、原样存；聚合层/维度层直接导入不重算；DWD 仅做加载期规范化，不重塑结构。**

---

## 一、核心原则

1. **三层分工**
   - **DIM 维度层**："是什么"（渠道/账号/厂商/笔记字典）。
   - **DWD 明细层**：每行一个客户或设备，保留完整漏斗原始字段。
   - **DWS 聚合层**：BI 图表直接读，按日/渠道/笔记预聚合（已是上游算好的）。
2. **原样存**：每张源表对应一张目标表，保留全部原始列；只在加载期做"规范化"（见第五节），不改列名、不合并、不发明阶段字段。
3. **维度表替代乱 mapping**：原 `account_agency_mapping` + `agency_abbreviation_mapping` 两张散乱映射表，统一由 `dim_account` + `dim_vendor`（来自 `申万宏源-投放账号映射表`）替代。
4. **两套漏斗不混表**：内容平台（加微链路）与应用市场（下载链路）漏斗阶段与粒度不同，分两张 DWD 明细表；在 DWS 层由 `agg_vendor_daily` 用"超集列"统一（APP* 列仅应用市场有值，开口/潜在客户列仅内容平台有值）。

---

## 二、数据源 → 目标表映射

| 源文件 | 粒度 | 类型 | 目标表 | 行数量级 |
|---|---|---|---|---|
| `申万宏源-投放账号映射表.xlsx` | 账号 | DIM | `dim_account` / `dim_vendor` | ~200 |
| `4线索明细【添加企微开始日期_2026-01-01】.xlsx` | 1 行=1 企微 | DWD | `fact_conv_content` | 大 |
| `8.1应用市场归因明细【下载_2026-01-01~2026-12-31】.xlsx` | 1 行=1 APP下载 | DWD | `fact_conv_appmarket` | 大（22MB） |
| `厂商广告投放分析.xlsx` (Sheet1) | 日×平台×厂商×业务模式 | DWS | `agg_vendor_daily` | 6215 |
| `6.1小红书笔记表【2026-01-01~2026-12-31】.xlsx` | 笔记级 | DWS | `agg_xhs_note` | 中 |
| `0.1开户渠道分析明细【2025-01-01~2026-06-30】.xlsx` (开户渠道分析) | 时间区间×渠道类别×渠道 | DWS | `agg_daily_channel_open` | 小 |

> 注：`厂商广告投放分析` 的 Sheet3（月×平台透视矩阵）与 Sheet2（空）不独立建表，可由 `agg_vendor_daily` 透视得到。

## 三、DIM 维度层

### 3.1 `dim_channel_category`（渠道类别字典，5 行预置）
| channel_category_id | name |
|---|---|
| 1 | 内容平台 |
| 2 | 应用市场 |
| 3 | 合作机构 |
| 4 | 员工开户 |
| 5 | 自然流入 |

### 3.2 `dim_channel`（渠道叶子，FK channel_category_id）
覆盖内容平台（抖音/腾讯/小红书/快手）、应用市场（小米/华为/OPPO/VIVO/荣耀/苹果；鸿蒙/iOS 先建"待上线"禁用行）、合作机构（工行/农行/建行/兴业…）、员工渠道（员工CRM/员工企微）。
> 来源：`4线索明细.平台来源`、`8.1.应用市场`/`应用市场名称`/`渠道类型`、`0.1.渠道名称` 的并集。

### 3.3 `dim_account`（投放账号维度，来自 `申万宏源-投放账号映射表`）
列：平台 / 主账号ID / 主账号名称 / 子账号ID / 子账号名称 / 代理商名称 / 代理商简称 / 代理商字母简称 / 业务模式；FK → `dim_channel`、`dim_vendor`。
> **直接替代**原 `account_agency_mapping` + `agency_abbreviation_mapping`。

### 3.4 `dim_vendor`（厂商/代理商字典，来自同一映射表去重）
列：代理商名称 / 代理商简称 / 代理商字母简称（lz/xz/zl/fs…）。
> 应用市场厂商为固定展示值（非计算），按固定维度录入即可。

### 3.5 时间维度：不建 `dim_date`
`agg_vendor_daily` 已自带 `日期`（日级）+ `月` 列，时间筛选/分组/同环比直接用该列做（SQL `date()`/`strftime()` 或 pandas `dt`），无需单独的日历维度表。建 `dim_date` 属过度设计（YAGNI）。

## 四、DWD 明细层（原样存，加代理主键 + 加载期规范化）

### 4.1 `fact_conv_content`（← `4线索明细`，1 行=1 企微）
原始 40 列全部保留，加 `id` 代理主键：
```
微信昵称, 资金账号, 开户营业部, 客户性别, 平台来源, 流量类型, 客户来源,
是否客户开口, 是否有效线索, 是否开户中断, 开户中断日期, 是否开户, 是否为有效户,
是否为存量客户, 是否为存量有效户, 是否删除企微,
线索日期, 首次触达时间, 最近互动时间, 互动次数, 营销人员互动次数,
添加员工号, 添加员工姓名, 开户时间, 微信认证状态, 微信认证时间, 有效户时间,
资产, 客户贡献,
广告账号, 广告代理商, 广告ID, 创意ID, 笔记ID, 笔记名称,
平台用户ID, 平台用户昵称, 广告点击日期, 生产者, 企微标签
```
> 加载期：布尔列(0/1) 归一；`nan`→NULL；`平台来源`/`广告代理商` 可挂 `dim_channel`/`dim_vendor` 外键（保留原文本列，外键为可选增强）。

### 4.2 `fact_conv_appmarket`（← `8.1应用市场归因明细`，1 行=1 APP下载）
原始 33 列全部保留，加 `id` 代理主键：
```
数据更新日期, 设备号, 应用市场, 投放账号, 下载日期, 广告计划ID, 注册手机号,
是否激活APP, APP激活时间, 是否开户注册, 注册开户流程时间, 是否注册身份证, 注册身份证时间,
是否注册银行卡, 注册银行卡时间, 是否提交开户, 提交开户时间, 是否开户成功, 开户成功时间,
是否新开户, 是否入金, 是否有效户, 有效户时间, 是否存量客户,
总资产, 累计创收, 人均日创收, 开户时间,
渠道类型, 应用市场名称, 是否创建完资金账号, 资金账号创建完成时间, 资金账号
```
> 加载期：布尔列(`是/否`) 归一为布尔；`nan`→NULL；`应用市场`/`渠道类型`/`应用市场名称` 可挂 `dim_channel` 外键。
> 该表保留了应用市场最细漏斗（激活APP→注册身份证→注册银行卡→提交开户→开户成功→入金→有效户），向上 roll 到 `agg_vendor_daily` 的 `APP下载数/APP激活人数/开户人数/有效户人数`。

## 五、DWS 聚合层（原样存，已是上游算好的）

### 5.1 `agg_vendor_daily`（← `厂商广告投放分析` Sheet1，6215 行）
日×平台×厂商×业务模式，**统一漏斗超集**：
```
日期, 月, 平台, 厂商, 业务模式,
花费, 展示量, 点击量, 线索数, APP下载数, 潜在客户数, 开口人数, APP激活人数,
有效线索数, 开户人数, 有效户人数, 客户资产, 客户创收, 存量客户资产,
点击率, 线索成本, APP下载成本, APP激活成本, 开户成本, 有效户成本, 线索转化率, 开户转化率
```
> 这是 BI 主指标表，覆盖两套漏斗（APP* 列仅应用市场有值，开口/潜在客户列仅内容平台有值）。

### 5.2 `agg_xhs_note`（← `6.1小红书笔记表`，笔记级）
24 列（**丢弃脏列 `Unnamed: 24`**）：
```
笔记ID, 笔记标题, 笔记类型, 内容类型, 笔记账号, 创作者, 广告策略, 发布时间,
总展现量, 点击量, 总点击率, 总互动量, 消费金额,
推广展现量, 推广点击量, 推广点击率, 推广互动量,
私信进线人数, 添加企微人数, 企微成功添加人数, 加微成本, 开户人数, 开户成本, 笔记链接
```
> 既是笔记维度又是笔记级聚合，单表承载（无需单独 `dim_note`）。

### 5.3 `agg_daily_channel_open`（← `0.1开户渠道分析明细`，时间区间×渠道类别×渠道）
8 列：
```
时间区间, 渠道类别, 渠道名称, 开户成功人数, 入金户数, 入金率, 有效户数, 有效户率
```
> 覆盖非广告渠道（员工开户/合作机构/自然流入），补全 `agg_vendor_daily` 只含广告渠道的缺口。

## 六、加载期规范化要点（不属于结构重塑）

| 问题 | 位置 | 处理 |
|---|---|---|
| 字符串 `'nan'` 不是空值 | `8.1`/`厂商` 多处 | 转 NULL |
| 布尔编码不一致 | `4线索明细` 用 0/1，`8.1` 用 是/否 | 统一为布尔 |
| 脏列 `Unnamed: 24` | `6.1` 末尾 | 丢弃 |
| 时间列混合 字符串/ datetime | 各表 | 解析为 DATE/DATETIME |
| 空 Sheet2 / 透视 Sheet3 | `厂商广告投放分析` | 不建表，由 `agg_vendor_daily` 透视 |

## 九、实现备注与已知差异（2026-07-07 ETL 落地后发现）

> 以下均为"原样存、不加 FK"原则的必然结果，非错误。若将来要做"明细→维度"强制关联，需先统一这些差异。

| 差异点 | 现象 | 影响 | 处理建议 |
|---|---|---|---|
| 内容明细平台列名 | `fact_conv_content` 源表无"平台"列，实际叫 `平台来源`/`平台用户ID`/`平台用户昵称` | 文档第六节写的 `channel_id(抖音·腾讯·小红书)` 关联应基于 `平台来源` 文本列 | 上层关联用 `平台来源` 比对 `dim_channel` |
| 渠道类别命名不统一 | `dim_channel_category` 用"内容平台/应用市场"；`agg_daily_channel_open.渠道类别` 实际值是"互联网引流/合作机构/自然流入/员工开户" | "互联网引流"≈"内容平台"，两套叫法 | 上层做映射表或统一命名 |
| `0.1` 缺应用市场类 | `agg_daily_channel_open` 渠道类别只有 4 类（无"应用市场"） | 该数据源是 2 月口径，应用市场当时未归入此类统计 | 正常，待后续数据源更新 |
| 应用市场大小写 | `fact_conv_appmarket.应用市场` 含 `oppo`/`vivo`(小写)，`dim_channel` 预置 `OPPO`/`VIVO`(大写) | 若按名关联会匹配不上 | 上层比对时 `upper()` 或统一小写 |
| `dim_channel` 字段名 | 实现为 `is_enabled`，文档第六节曾写 `is_active` | 仅文档笔误 | 以实现 `is_enabled` 为准 |

### ETL 脚本
`scripts/import_v2_schema.py`（pandas 读 Excel → SQLAlchemy 落 SQLite，含 `'nan'→NULL`、`是/否→布尔`、超长整数转 TEXT 等规范化）。重跑前会 `replace` 新表，不动旧表。
