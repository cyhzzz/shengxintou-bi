# 新需求开发工作流

## 目标

在不突破数据职责边界和业务口径的前提下，把需求变成可验证、可追溯的最小实现。流程允许小任务简化文档，但不能跳过事实核对和验证。

## 1. 建立基线

1. 读取根规则与任务涉及的专题规则。
2. 记录 `git status --short --branch`，识别用户原有改动。
3. 执行或确认首次 setup 已完成；不要在每个子任务重复安装依赖。
4. 从 `version.json`、构建清单、router、模型和端点读取当前事实，不从历史 changelog 推断现状。

## 2. 需求拆解

输出最小需求表：

| 验收项 | 类型 | 涉及模块 | 数据来源/权威源 | 非目标 | 验证方式 |
| --- | --- | --- | --- | --- | --- |

必须澄清：

- 用户真正要改变的行为。
- 输入、输出、筛选、权限、空状态和错误状态。
- 是否影响新开户/存量、漏斗、资产、主播或应用市场口径。
- 是否需要新增数据源；若需要，业务加工应在上游还是本项目。
- 是否改变 API、Schema、路由、生成类型或发布产物。

## 3. 代码定位

使用由粗到细的定位方式：

1. 从 `docs/rules/overview.md` 判断候选模块。
2. 读取 router、蓝图注册、service 或模型等稳定入口。
3. 用 `rg` 搜索端点、字段、组件、表名和相同业务术语。
4. 跟踪从 UI → service → API → query → table 的调用链，或反向跟踪。
5. 找到同类实现，确认可复用组件、响应结构和测试位置。
6. 列出最终改动点与理由；没有证据的候选不进入方案。

## 4. 设计门禁

出现以下任一情况时，先使用 `docs/rules/templates/tech-spec.md`：

- 新功能、用户可见行为变化或跨模块修改。
- 数据口径、Schema、导入模式、API 契约或路由变化。
- 有两个以上合理方案，或回滚成本高。
- 改动涉及外部服务、发布流程、权限或用户数据。

设计至少说明要做/不做、现状证据、方案取舍、不变式、风险、验收和验证。获得必要确认后再实施。

spec 文件复制到 `docs/superpowers/specs/`（已 gitignore，不入仓库），命名建议 `YYYY-MM-DD-需求名.md`。

## 5. 实现

1. 先修改权威源，再更新消费者和兼容层。
2. 复用现有公共组件、service、filter adapter 和异常处理。
3. 不新增下游业务 mapping 或口径修补。
4. 不夹带无关重构；发现无关问题记录在交付说明中。
5. 新端点同步响应类型和 smoke；新 lazy 路由同步路由 smoke。
6. 新 UI 同步加载、空、错、窄屏和详情状态。
7. 新数据导入类型同步后端类型、handler、目标表、前端入口、指南和测试。

## 6. 验证

按 `testing-and-delivery.md` 的影响映射执行：

1. 语法/类型检查。
2. 最相关的单元、smoke 或回归测试。
3. 构建验证。
4. 必要的路由或功能测试。
5. `git diff --check` 和最终工作区审计。

对 UI 变化进行视觉或交互验证；对数据变化使用可解释样例核对分子、分母、过滤前后和空值。

## 7. 沉淀与交付

- 只有稳定架构、公共契约或高风险不变式变化时才更新 `docs/rules/`。
- 用户使用方式变化时更新 README 或导入指南。
- 当前版本历史只更新 `version.json`，且通常在明确发版时处理。
- 交付说明列出改动、验证、未运行项、基线问题和未提交文件。
- 未经明确要求，不 commit、push、tag 或 release。

### 是否需要更新规则文档（判断清单）

按 `testing-and-delivery.md` 第 13 节的清单判断：

- 涉及业务口径/导入类型/三端差异/工具链/打包流程/测试体系/公共组件契约/架构契约 → 必须更新对应规则文件。
- 单个 Bug 修复/UI 微调/性能优化 → 不更新规则。
- 更新规则后必须运行 `python scripts/check_rule_architecture.py` 并同步 `AGENTS.md` / `CLAUDE.md` / `.workbuddy/memory/MEMORY.md`。

### 是否需要建议用户手动触发验证

按 `testing-and-delivery.md` 第 11.2 节的清单判断：

- 涉及桌面版打包相关 → 建议触发 `scripts\build-installer.ps1`。
- 涉及移动端 `services/mobile*.ts` 或 `capacitor.config.ts` → 建议触发 `cd android && npm run build:apk`。
- 移动端 Bug 修复 → 建议触发 `python tests\mobile\smoke_test.py`。
- 跨模块或发版前 → 建议触发 `scripts\run-full-tests.bat`。

在交付说明末尾添加"建议触发"段落，明确命令和原因。

## 完成检查

- [ ] 每个验收项都有实现和直接证据。
- [ ] 所有非目标均未被意外纳入。
- [ ] 业务不变式未被破坏。
- [ ] 生成文件和权威源处理正确。
- [ ] 测试范围与影响范围匹配。
- [ ] 用户原有改动未被覆盖。
